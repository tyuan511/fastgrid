# 本地加密与跨端同步

状态：**本地加密已实现**（`fg-crypto`、`fg-store`）；**同步尚未实现**，排在 [M9](roadmap.md)，但数据结构从第一天起就为它预留。

## 目标与威胁模型

所有连接数据（配置、分组、密码、片段、草稿、历史与审计里的 SQL、UI 状态、设置）都加密保存在本地，并且将来可以在多台设备之间同步，同步存储方（WebDAV、S3 等）看不到明文。

| 能防住 | 防不住 |
|---|---|
| 磁盘、备份、云盘里的存储文件被拷走 | 以你的身份运行、并能访问钥匙串的恶意软件 |
| 同一台机器上其他用户读取数据文件 | 应用解锁期间的内存抓取 |
| 同步存储方（对象存储 / WebDAV 服务器）被攻破或被审查 | 你自己泄露同步密码或导出密码 |
| 备份文件（`.bak-vN`）、WAL 文件中的残留 | 存储方能看到的元数据（见下） |

## 密钥

```
设备密钥  (256 位随机，存在系统钥匙串，按 store_id 命名)
   └─ 加密本地存储里的每一条记录
同步密码  (用户设置，仅开启同步后)
   └─ Argon2id → 包装一把随机的同步密钥 → 加密推送到远端的数据
导出密码  (每次导出 / 导入时输入)
   └─ Argon2id → 加密备份文件
```

两层完全分开：**本地落盘用设备密钥，传输与远端存储用同步密钥，备份文件用导出密码。** 每台设备的设备密钥互不相同，也不需要共享。

### 设备密钥

- 首次创建存储时随机生成，通过 `DeviceKeyProvider` 交给钥匙串（macOS Keychain / Windows Credential Manager / Secret Service）。应用层实现在 `fg-service`，`fg-store` 只依赖这个 trait。
- **开发环境优化**：在开发构建（debug 模式或 `FASTGRID_DEV=1`）下，应用默认使用文件后端（`data_dir/.dev-keyring.json`，权限 `0600`）持久化设备密钥，若文件尚无条目则回落到系统钥匙串读取并自动缓存。这样既避免了本地开发重新编译后每次启动都被系统钥匙串弹窗请求密码，又保证了开发数据在多次重启间不丢失。生产构建（release）依然默认强制使用系统钥匙串。可通过环境变量覆盖：
  - `FASTGRID_KEYCHAIN=memory` 或 `FASTGRID_MEMORY_KEYCHAIN=1`：纯内存模式，退出即丢弃。
  - `FASTGRID_KEYCHAIN=os` 或 `FASTGRID_USE_OS_KEYCHAIN=1`：强制使用系统钥匙串。
  - `FASTGRID_KEYCHAIN=file`：强制纯文件后端，不回退系统钥匙串。
  - `FASTGRID_KEYCHAIN=dev`：文件后端并在未命中时回退系统钥匙串迁移。
- 钥匙串的条目以 `store_id` 命名，所以把存储文件拷到另一台机器不会误用别的密钥。
- 存储里有一条用设备密钥加密的**校验值**（`meta.key_check`）。启动时验证密钥是否匹配：
  - 钥匙串里没有 → `Error::KeyUnavailable`（重装系统、钥匙串被重置）。
  - 钥匙串里的密钥不对 → `Error::KeyUnavailable`。
  - 两种情况都**不会改动存储文件，也不会生成新密钥覆盖旧的**。
- 无法恢复的情形：钥匙串丢失且没有同步、没有加密备份。因此产品要引导用户**开启同步或定期导出加密备份**。没有恢复密钥、没有主密码，这是有意的简化。

### 同步密码与同步密钥（M9）

- 开启同步时用户设一个同步密码。远端存放一把**随机同步密钥**，由「同步密码派生的密钥」包装（`password_seal`）。所有同步数据用同步密钥加密。
- 这样修改同步密码只需重新包装同步密钥，不必重新加密远端全部数据。
- 新设备输入同步密码即可解开同步密钥并拉取数据，不需要设备配对。
- 忘记同步密码：任何仍保留本地数据的设备可以「重置同步」，重新生成同步密钥并重新推送。

### 导出 / 导入

- 导出：用设备密钥解密 → 用「导出密码派生的密钥」重新加密为单个文件（格式见下）。导入同一密码。
- **没有明文导出。** "可移植的解密文件"指脱离设备密钥、可在任何设备用密码打开的文件。
- 范围：`Connections`（连接、分组、片段）或 `Everything`（含历史、审计、草稿、UI 状态、设置）；密码类 secret 可选择是否包含，但始终只在加密文件内。
- 导入是显式用户操作，所以偏宽松：仅当本地已有**更新的活动版本**时跳过；已被删除的记录会复活，并获得新的版本号，因此同步时也会赢过旧的删除标记。

## 加密格式

### 记录封装（`fg-crypto::seal`）

```
byte 0       格式版本 (1)
byte 1       算法 (1 = XChaCha20-Poly1305)
bytes 2..6   key_id，u32 大端：用哪一代密钥加密（用于以后轮换）
bytes 6..30  nonce，24 字节随机
bytes 30..   密文 || 16 字节认证标签
```

- 选 XChaCha20-Poly1305：192 位随机 nonce 可以在各设备**独立随机生成**而不冲突，不需要计数器，这是多设备同步的前提。
- 头部与「上下文」都参与认证。记录的上下文是 `fg-rec|<kind>|<id>`：把一条密文复制到别的行或别的表会解密失败，不会被悄悄接受。
- 版本号高于本版本 → 明确报「由更新版本写入」，不会误读。

### 口令保护文件（`fg-crypto::password_seal`）

```
"FGPW" | 版本 (1) | kdf_len u16 | KDF 参数 JSON | 记录封装
```

- KDF 参数（Argon2id：64 MiB、3 轮、1 并行、16 字节随机盐）随文件保存，所以以后可以提高成本而不影响旧文件。
- 魔数、版本、KDF 参数与调用方上下文（导出为 `fastgrid-export-v1`）全部参与认证。
- 备份内容是 `{format_version, exported_at, source_store_id, records[]}` 的 JSON，再整体加密。

## 哪些内容是明文

`record` 表里只有结构性列：

| 列 | 说明 |
|---|---|
| `kind` | 记录种类（`connection`、`history`……） |
| `id` | 随机 UUIDv7（或由 UUID 组成的复合键）。**不含**连接名、表名等有意义的内容 |
| `parent_id` | 所属记录的 ID（历史属于哪个连接） |
| `sort_ts` | 排序时间戳（历史的执行时间等） |
| `rev`、`device_id`、`updated_at`、`deleted_at`、`dirty`、`key_id` | 同步所需的记账信息 |

其余全部在 `enc` 里：连接名、主机、用户、SSH、备注、分组名、密码、SQL 文本、表名、过滤条件、设置。

后果与取舍：

- 连接列表在内存中按名称排序（名称是密文，无法用 SQL 排序）；连接数量级是几十到几百。
- 历史搜索解密最近 5000 条后在内存里过滤。
- 表视图（过滤、列宽）的记录 ID 是随机的，查找时读取该连接下全部视图再匹配，避免把表名放进明文 ID。
- `PRAGMA secure_delete = ON`，删除的页会被覆盖；删除用墓碑（保留记账信息、清空密文）。
- 存储方（以及能看到存储文件的人）能看到：记录数量、各种类的数量、时间戳、大致大小、随机 ID 与设备 ID。

## 同步设计（M9，尚未实现）

### 不运营服务器

支持「自带存储」：**S3 及兼容服务**（R2、MinIO、B2）、**WebDAV**（Nextcloud、群晖、坚果云）、**本地文件夹**（顺带让 iCloud Drive、Dropbox、Syncthing 可用）。它们都只有 `list / get / put / delete`，没有服务端逻辑，所以协议按「笨存储」设计。

### 每台设备只写自己的文件

```
fastgrid-sync/
  manifest                 格式版本、保险库 ID
  keys/                    被同步密码包装的同步密钥
  devices/<设备ID>/
    seg-000001 ...         这台设备产生的变更批次（同步密钥加密，写入后不再修改）
  snapshots/               定期压缩的全量快照
```

- 每个文件只有一个写入者 → 不需要锁，不需要 ETag 比较并交换，文件夹同步工具也不会产生"冲突副本"。S3 的条件写（`If-None-Match`）可用于防止重复创建分段。
- 拉取：列出其他设备目录，只下载本地游标之后的分段。游标存在本地 `sync_state` 表，不同步。
- 推送：`dirty_records()` 取出本地变更 → 写入新分段 → 成功后 `mark_clean()`。若记录在推送过程中又被修改（`rev` 变了），它**保持脏**，不会丢改动。
- 压缩：任意设备写全量快照；旧分段在所有已知设备都确认拉取后才清理。

### 合并规则

两个版本冲突时：**`rev` 高者胜；相同则 `updated_at` 晚者胜；再相同则 `device_id` 大者胜。** 所有设备得出一致结论。

- 删除是墓碑，同样参与比较；旧版本无法让已删除的记录复活。
- 拉取下来的记录以「干净」状态写入（不会又推回去），并保留远端的 `rev`/`device_id`。
- 日志类记录（历史、审计）只追加、ID 全局唯一，实际是并集合并。
- 同步范围：连接、分组、secret、片段、草稿、历史、审计、表视图、设置、各设备的工作区布局（按设备分开存，互不覆盖）。**`mcp_client` 令牌属于单台设备，永不同步、也不导出。**
- 文本草稿的冲突保留一份「冲突副本」，不静默覆盖（M9 实现）。

### 已知限制

- 存储方能看到元数据（见上）；设备目录名使用随机 ID。
- WebDAV 实现差异大，协议不依赖 ETag 与 LIST 的强一致，同步是轮询级别的，不是实时推送。
- 撤销一台设备：轮换同步密钥后它读不到**新**数据，但已经拉走的历史无法收回。
- 排序主要靠 `rev`，墙钟时间只是次级依据，容忍设备时钟偏差。
- S3 / WebDAV 的凭据本身是 secret，默认只保存在本机、不同步。

## 已实现的构件
